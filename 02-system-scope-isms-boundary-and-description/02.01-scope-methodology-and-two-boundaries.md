## 1. Purpose

Every programme running two frameworks at once reaches the same fork within its first month. Somebody
senior asks whether the two scopes can be the same scope, because one boundary is easier to explain to a
board, easier to maintain, easier to put in a slide, and produces one number instead of two. The question
is entirely reasonable and the answer is no.

It is no because the two boundaries are not two versions of the same object. A SOC 2 scope is a **system**:
a bounded set of infrastructure, software, people, procedures and data assembled to deliver a defined
service to defined users. An ISO/IEC 27001 scope is an **ISMS boundary**: an organisational perimeter
inside which a management system operates. One is defined by what delivers a service; the other is defined
by what the organisation manages. Those definitions select different things, and no amount of good will
makes them select the same things.

This document records how each boundary was derived, what was tested at the edge of each, and the argument
that **neither boundary contains the other** — an argument this phase must win, because if it is wrong then
either the system description is inflated or the certificate is narrower than the company. It records
**ADR-0006** and **DEC-201**, both decided by Karim Haddad on 2026-02-20.

## 2. The two boundaries

| | SOC 2 system scope | ISO 27001 ISMS scope |
|---|---|---|
| What it is | A **system**: infrastructure, software, people, procedures and data serving a defined service | A **management system boundary**: an organisational perimeter |
| Defined by | Management, described under **DC section 200**, DC3 | The organisation, under **clause 4.3**, considering 4.1, 4.2 and interfaces/dependencies |
| Here | The **CloudNimbus Workforce Platform** — the multi-tenant production service | **The whole of CloudNimbus, Inc.** — 187 staff, all locations, all information assets |
| Contains things the other does not | AWS and Halcyon Identity infrastructure — carved out but inside the system | Corporate functions: the finance ledger, the CRM as pipeline system of record, sales and marketing operations |
| Excluded | Non-production environments; the professional services / implementation offering; corporate back-office systems that do not serve the platform | Nothing. No organisational unit, location or asset class is excluded from the ISMS boundary |

Read the fourth row twice. It is the row that makes this a real argument rather than a presentational one:
each boundary contains something the other does not, in both directions, at the same time.

## 3. How the system boundary was derived

The system boundary was derived **downward from the service commitments**, not upward from an asset list.
The order matters, because an asset list will always answer the question "what do we have?" and never the
question "what has to be true for this promise to hold?"

The method had four steps. First, the commitments CloudNimbus has actually made were extracted from
executed contracts rather than from marketing material — the availability commitment, the incident
notification commitment, the deletion and certification commitment, the EU residency commitment, the
encryption commitment, the calculation accuracy commitment, and the rest, recorded as SC-01 to SC-10 in
02.12. Second, each commitment was reduced to what the system must **do** to keep it, producing SR-01 to
SR-12. Third, every component whose failure would break one of those system requirements was pulled into
the boundary. Fourth — and this is the step that most scoping exercises skip — every component that
survived step three was challenged with the reverse question: if this component were removed, which system
requirement would fail? A component that cannot be attached to a requirement is not in the system; it is
merely nearby.

That reverse test is what excluded the corporate back office. CloudNimbus's finance ledger holds customer
billing data and is important to the company. No system requirement fails if it stops. It cannot break
availability of the platform, it does not touch tenant data, it is not on any path a data flow traverses,
and no trust services criterion is met or missed by anything it does. It is in the ISMS, where it belongs,
and it is out of the system. The same reasoning excluded the CRM as a system of record for sales pipeline,
the marketing estate, and the recruiting tooling.

It also excluded the **professional services and implementation offering**, recorded as **DEC-204**,
decided by Nathan Oyelaran on 2026-02-27. This was the least comfortable of the exclusions and deserves its
reasoning stated rather than assumed. Implementation consultants work inside customer tenants during
onboarding, with elevated access, on real data. The argument for including the offering was that this
access is exactly the kind of thing a reader of a system description would want covered. The argument that
won was that the professional services offering is a **different service** — scoped by statement of work,
priced separately, delivered by people, not by the platform — and that describing it inside the system
description of a software service would produce a description of two services in a report that opines on
one. The residue is handled where it actually lives: the consultants' *access to the production platform*
is inside the system, because it is platform access like any other, and it is governed by the same access
tiers set out in 02.05. What is out of scope is the engagement, the methodology and the deliverables, not
the access.

## 4. How the ISMS boundary was derived

The ISMS boundary was derived under **clause 4.3**, which requires the organisation to determine the
boundaries and applicability of the ISMS considering the external and internal issues determined under 4.1,
the requirements of interested parties determined under 4.2, and the interfaces and dependencies between
activities performed by the organisation and those performed by other organisations. That third
consideration is the one most often left out, and it is precisely where AWS and Halcyon Identity sit; 02.08
walks all three in full.

Applied at CloudNimbus, the clause produced a boundary of **the whole organisation**: all 187 staff across
31 US states and 4 countries, all locations including home-working arrangements, and all information
assets. This was decided in Phase 01 as **DEC-103** and **ADR-0003** and is not reopened here. What Phase
02 adds is the test of whether it survives contact with an inventory, and it does: of the 1,046 assets
recorded in 02.06, every one has an owner, a classification and a place inside the ISMS, because there is
no organisational unit for an asset to fall outside of.

The narrow alternative — an ISMS scoped to platform engineering — is the one most SaaS companies of this
size choose, and it fails here on two grounds. It fails on honesty, because in a remote-first company where
Customer Success staff open support sessions into customer tenants and Sales staff receive customer data in
security questionnaires and procurement threads, a boundary drawn around engineering would certify the
population least likely to mishandle customer data while excluding the population most likely to. And it
fails commercially, for the reason 02.08 develops: the scope statement is printed on the certificate, and a
prospective enterprise customer reading "the platform engineering function" has been handed their next
question rather than an answer to their current one.

## 5. What was tested at the edge

A boundary is only as good as the cases that nearly fell the other way. Six were argued.

The **analytics read replica** is in the system. It holds customer data, the reporting API serves customer
queries from it, and SR-01 — tenant isolation on every access path — must hold there as much as on the
primary. Calling it "just a replica" would have removed the single most interesting access path in the
platform from the description. It is in, and 02.04 explains at length why it matters.

The **Customer Success support console** is in the system. Support access is a data flow, DF-12, that
reaches customer personal data under a scoped session. A description that omitted it would omit one of the
few paths by which a CloudNimbus employee reaches a named individual's records.

The **CRM** is out of the system and in the ISMS. It holds customer contact data and some of what customers
tell Sales during procurement, which is why it is squarely an ISMS asset with an owner and a
classification. It serves no system requirement.

**Contractor and sales laptops** are in the ISMS and mostly out of the system, and this is the boundary
case that produces the 164-of-187 people figure in 02.05. The rule that decides an endpoint has two limbs,
and both are needed: **an endpoint is in the system when the person operating it can reach production or
customer data, or when the device is used to build, test or validate software that forms part of the
system.** Otherwise it is an ISMS asset only.

The second limb exists because the first limb alone gives the wrong answer for the **44 test and lab
devices** in 02.06. Those devices hold no customer data and reach no production environment — the iOS and
Android handsets and the browser and accessibility rigs the four client applications are validated on are
non-production by construction. They are nonetheless part of how the software in the system comes to be
what it is: an application binary that reaches 1.24 million people was built and validated on them, and a
device that can alter a build or sign an artefact is a route into the system whatever data it holds. A rule
drawn on data access alone would have put the test estate outside the description and left the change
pipeline that ADR-0007 keeps in scope depending on equipment nobody described. 02.06 §7 applies the second
limb to those 44 explicitly.

The **non-production AWS accounts** are out of the system on the strength of SR-12, and 02.03 states
plainly that this is a claim about a control rather than a fact about the architecture.

**Home-working locations** are inside the ISMS and are not "sites" in the system. The Denver suite, ~4,100
sq ft with no server, no network closet and no comms room, is a meeting space; there is no data centre and
no production equipment anywhere on premises. The physical dimension of the system is therefore AWS's, and
AWS is carved out.

## 6. Neither boundary contains the other

Here is the claim, stated without hedging.

**The SOC 2 system reaches outward past the ISMS boundary.** The system includes infrastructure operated by
**Amazon Web Services** and identity services operated by **Halcyon Identity, Inc.** Those components are
part of the system as DC3 defines it — they are infrastructure and software the service runs on, and
without them the service does not exist. They are not, and cannot be, inside CloudNimbus's ISMS.
CloudNimbus does not operate AWS's data centres, cannot assign an owner to a Halcyon control, cannot
subject either to its own clause 9.2 internal audit programme, and cannot make either the subject of a
clause 6.1.3 risk treatment decision it is capable of executing. What CloudNimbus can manage is the
**interface**: supplier selection, contractual terms, its own configuration, and its monitoring of the
relationship. That is exactly what clause 4.3 c) contemplates and exactly what the **carve-out** method in
DEC-108 contemplates. A management system that claimed a supplier's controls as its own would be a
management system making a claim it cannot discharge.

**The ISMS reaches outward past the SOC 2 system.** The ISMS covers all 187 staff, the corporate functions,
the finance ledger, the CRM, the marketing estate, the internal SaaS applications used by Sales and G&amp;A,
and the procedures that govern them. None of that serves a trust services criterion. A reader of the
examination report has no interest in how CloudNimbus secures its own pipeline forecasts, and putting them
in a system description would inflate it with material the service auditor would then have to test for no
benefit to any user entity. **02.06 quantifies this direction precisely: 1,046 − 800 = 246 assets sit
inside the ISMS and outside the SOC 2 system.**

The two directions are not symmetrical in how they can be counted, and 02.06 says why: the outward reach of
the system is real but unnumbered, because CloudNimbus does not own or inventory a supplier's components.

## 7. Why forcing them together would be worse

There are only two ways to make one boundary out of two, and both are worse than living with two.

**Narrow the ISMS to match the system.** This means excluding organisational units — Sales, Marketing,
Finance, part of G&amp;A — from the ISMS so that its perimeter matches the platform. The cost is a
certificate whose scope statement excludes the people who handle customer data outside the product, and an
ISMS that cannot honestly address A.6-series people controls for a third of the company. It also solves
nothing on the SOC 2 side, because the system would still contain AWS and Halcyon and the ISMS still could
not.

**Widen the system to match the ISMS.** This means describing the finance ledger, the CRM and the
implementation practice inside a system description, and then either claiming AWS and Halcyon inside a
management system CloudNimbus does not operate, or leaving them out of the system entirely — which would be
a false description, since the service demonstrably runs on them. The first is a claim that cannot be
supported at Stage 2. The second is a description defect of the most serious kind, because it omits
components on which the service depends.

So the programme holds two boundaries and reconciles them at the level of the individual control and the
individual asset rather than at the level of the perimeter. Each asset in 02.06 carries two flags rather
than one; each control in the Phase 04 library will record which framework it serves and which boundary it
sits in. That is more bookkeeping. It is also the only version of this that is true.

## 8. Decision record

**ADR-0006 — Two boundaries, deliberately different, neither containing the other.** Decided by Karim
Haddad on 2026-02-20; logged as **DEC-201**. Alternatives considered and rejected: narrowing the ISMS to
platform engineering to match the system, rejected on the honesty and commercial grounds in §4 and §7; and
widening the system to the whole organisation to match the ISMS, rejected because it would describe
services the report does not opine on and would force a false position on AWS and Halcyon Identity.
Related records: DEC-103 and ADR-0003 (ISMS scope is the whole organisation), DEC-108 (carve-out method),
DEC-202 and ADR-0007 (non-production exclusion), DEC-204 (professional services exclusion).
