## 1. Purpose

Section III of a SOC 2 report is management's description of the system. It is written by CloudNimbus, not
by the service auditor, and the auditor's opinion covers whether it is **presented in accordance with the
description criteria** as well as whether the controls were suitably designed and operated effectively.
That first limb is easy to underrate. A description can be entirely truthful and still fail, because it
omitted a criterion the description criteria require it to address.

This document is where the description begins. It answers DC1 — the types of services provided — sets out
the five components of the system under DC3, maps every one of the nine description criteria to the
document that answers it, and records what was excluded from the system and on what basis.

## 2. The DC section 200 coverage map

The applicable description criteria are **DC section 200, *2018 Description Criteria for a Description of a
Service Organization's System in a SOC 2 Report***, criteria DC1 to DC9.

| Criterion | Subject | Answered in |
|---|---|---|
| DC1 | Types of services provided | 02.02 |
| DC2 | Principal service commitments and system requirements | 02.12 |
| DC3 | Components of the system — infrastructure, software, people, procedures, data | 02.02, 02.03, 02.04, 02.05 |
| DC4 | Disclosures about incidents | Phase 06 — no reportable incident has occurred as at this phase's vantage |
| DC5 | Applicable trust services criteria and related controls | Phase 04 |
| DC6 | Complementary user entity controls | 02.11 |
| DC7 | Subservice organisations, the method used, and complementary subservice organisation controls | 02.10 |
| DC8 | Specific criteria not relevant to the system, and why | Phase 04 |
| DC9 | Relevant changes during the period | Phase 09 |

**Phase 02 answers five of the nine description criteria — DC1, DC2, DC3, DC6 and DC7 — and names where
the other four are answered.** DC5 and DC8 wait for the control library, because a description of which
criteria are addressed by which controls cannot precede the controls. DC4 waits for Phase 06 and, as at
2026-03-31, has nothing to report. DC9 waits for Phase 09 because the observation window opens on
2026-07-01 and there is no period yet for changes to occur during.

The reason for building the map now rather than later is a failure mode worth naming. **A description
assembled at the end of the period out of whatever documents happen to exist by then is how descriptions
come to omit DC4 and DC9.** Those two criteria are the ones nobody writes in advance: DC4 requires
disclosing incidents, which means somebody must have been recording them against the criterion rather than
only in a ticket queue, and DC9 requires identifying relevant changes during the period, which means
somebody must have been noticing changes as changes rather than as ordinary work. A team that starts
writing its description in January for a period that ended in December will reconstruct DC1 and DC3
comfortably from architecture diagrams, and will find that the evidence for DC4 and DC9 is in people's
memories. Mapping the criteria to owners and documents at the start of the programme is the cheapest
available insurance against that.

## 3. DC1 — the types of services provided

CloudNimbus, Inc. is a Delaware C-corporation founded in 2019, headquartered in Denver, Colorado, and
operating remote-first with 187 staff across 31 US states and 4 countries. It provides one service to
customers: the **CloudNimbus Workforce Platform**, delivered as multi-tenant software-as-a-service.

The customers are **640 employers**, mid-market organisations of between 500 and 15,000 employees each. The
people who use the platform day to day are those employers' employees — approximately **1.24 million**
individuals. That distinction runs through the whole description and is the reason several later arguments
land where they do: the party that signs the contract is not the party whose personal data the platform
holds, and the second party has no contractual channel to CloudNimbus at all.

The platform does five things.

**Time capture** records when an employee starts work, stops work, takes a break and moves between cost
centres, through the mobile applications and the web application. **Scheduling** publishes shifts, records assignment and acceptance, and
feeds the expected-versus-actual comparison the customer's operations managers work from. **Absence and
leave accrual** records absence against a controlled list of leave types and maintains entitlement and
accrual balances against the customer's own policy configuration. **Expense capture and policy evaluation**
takes a receipt image and an expense claim, extracts the fields, and evaluates the claim against the
employer's expense policy before routing it for approval. And the **calculation engine** derives the
numbers: overtime, shift differentials, accrual balances and reimbursement amounts, computed from the
customer's configured pay rules against the captured records, and output to the customer's payroll provider
through the integration tier.

That last capability is why this system description is not an ordinary one. **The output of the calculation
engine becomes a person's pay.** A defect in an availability control produces an outage, which is visible,
bounded and recoverable. A defect in the calculation engine produces a number that is wrong, that looks
exactly like a number that is right, and that may reach an individual's bank account through a payroll
provider before anybody notices. This is the rare software-as-a-service business where Processing Integrity
is the product rather than a formality, and 01.05 records that as the reason the category was selected
rather than avoided.

Service delivery spans three AWS regions: `us-east-1` as primary, `us-west-2` as warm standby and disaster
recovery, and `eu-central-1`, which serves the **41 customers** whose contracts require EU data residency.
There is no on-premises infrastructure anywhere in the service; the Denver suite is approximately 4,100
square feet of meeting space with no server, no network closet and no comms room.

The service is consumed through four client applications — the customer web application used by employees,
the tenant administration console used by the employer's HR and operations administrators, and the iOS and
Android applications — and through a documented REST API used for integration with customers' HR systems
of record and payroll providers.

## 4. The five DC3 system components

DC3 requires the description to identify the components of the system used to provide the services:
**infrastructure, software, people, procedures and data**. The populations below are the components inside
the SOC 2 system boundary. Where a figure is smaller than the organisation's total, the difference is the
boundary at work and is explained in the document named against it.

| Component | Population in the SOC 2 system |
|---|---|
| Infrastructure | 5 AWS accounts · 3 EKS clusters · 5 Aurora clusters · 17 non-Aurora data stores · 168 S3 buckets |
| Software | 63 microservices · 4 client applications — the customer web application, the tenant admin console, the iOS application and the Android application |
| People | **164 of 187 personnel.** The 23 outside are sales and marketing staff with no access to customer data or the production environment. They remain inside the ISMS |
| Procedures | 78 of 130 documented procedures |
| Data | The 12 personal data categories PD-01 to PD-12, plus tenant configuration, pay rules, calculation output and audit logs |

**187 − 164 = 23.** The rule that produces those two numbers is stated once, at 02.05 §3: a person is in
the people component if they either can reach the production environment or customer data, or operate a
documented procedure the system depends on. The twenty-three outside are the quota-carrying sales and
marketing personnel — account executives, sales development representatives, and the marketing function —
who satisfy neither limb: no production access, no support console access, no route to customer data
through the platform, and no in-scope procedure. Engineering, Customer Success, Product and Security are
wholly inside on the first limb, and the People, Legal, Finance and business-operations staff who run
screening, onboarding, offboarding, access administration and sub-processor administration are inside on
the second, whatever access they hold. They are not a rounding error and the twenty-three are not excluded
from the company's security programme: **all twenty-three remain inside the ISMS**, with managed endpoints,
mandatory awareness training, the same joiner-mover-leaver process and the same acceptable use obligations
as everybody else. What they are outside is the *system component* called "people" in a description of a
service they do not operate. 02.05 sets out the access tiers that apply the first limb, and makes the
argument that this is not a contradiction but the two-boundary model doing exactly what it was designed to
do.

The infrastructure component is detailed in 02.03, which sets out the seven AWS accounts and why five are
in the system, the six Aurora clusters and why five are, the EKS and networking design, the region
strategy, and the role of the `cnb-security` account as a separate trust domain. The software component and
the twelve principal data flows DF-01 to DF-12 are detailed in 02.04. The people and procedures components
are detailed in 02.05. The data component is detailed in 02.06 for information assets generally and in
02.07 for personal information specifically.

One point about the data component belongs here rather than downstream. The description criteria treat data
as a component of the system in its own right, not as a property of the stores that hold it. That framing
is useful, because it forces the question of what the system holds to be answered independently of where it
happens to sit — which is the only way a deletion commitment can be described honestly across a platform
where the same tenant's records exist in Aurora, in S3, in a search index, in a cache, in a Kafka topic and
in a backup snapshot at the same moment.

## 5. What is excluded from the system, and why

Three exclusions were taken deliberately, each recorded.

**Non-production environments.** The `cnb-staging` and `cnb-dev` AWS accounts, the fourth EKS cluster and
the `staging-core` Aurora cluster are outside the system. The exclusion rests on **SR-12** — non-production
environments hold no production customer data — recorded as **DEC-202** on 2026-02-24 and argued in full as
**ADR-0007** in 02.03. The change-management pipeline that promotes code *through* those environments
remains inside the system, which is why the code repository and CI/CD populations in 02.06 keep most of
their count. 02.03 states in terms what this exclusion actually rests on, and it is not the architecture.

**The professional services and implementation offering.** Recorded as **DEC-204**, decided by Nathan
Oyelaran on 2026-02-27. Implementation is a separate service, scoped by statement of work, priced
separately and delivered by people rather than by the platform. Describing it inside the system description
of a software service would produce a description of two services in a report whose opinion addresses one.
What is *not* excluded is implementation consultants' access to the production platform: that is platform
access, it is inside the system, and it is governed by the access tiers in 02.05.

**Corporate back-office systems that do not serve the platform.** The finance ledger, the CRM as system of
record for sales pipeline, the marketing estate and the recruiting tooling. Each was tested with the
question 02.01 §3 sets out — if this stopped, which system requirement would fail? — and each survived the
question intact, which is to say none of them can break one. All of them remain inside the ISMS.

The honest way to read these three exclusions together is that the first is contingent on a control, the
second is a judgement about what service is being described, and the third is a straightforward
application of the boundary test. They are not equally robust, and 02.13 records the first as the one to
watch.

## 6. What this description is not

Two clarifications, because a system description invites both misreadings.

It is not an assertion that the controls are effective. That assertion is management's, made in Section II
of the report, and the opinion on it is the service auditor's, in Section I. A description says what the
system **is**; the criteria and controls are Phase 04's subject and the testing is Phase 08's.

And it is not a general-use document. The SOC 2 report that will carry this description is
**restricted-use**: intended for CloudNimbus's management, for user entities during the period covered, and
for other specified parties with sufficient knowledge and understanding to read it properly. It is provided
under non-disclosure agreement. Nothing in this description should be written as though it will be
published, because it will not be.
