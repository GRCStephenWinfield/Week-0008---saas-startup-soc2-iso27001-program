Every proposed complementary user entity control is assessed on this form before it reaches the
description. Fifteen were proposed in Phase 02 and four were refused; the form exists so that the fifth
refusal is as easy as the first.

| Field | Guidance |
|---|---|
| Proposed CUEC | The control as drafted, in the customer's language |
| Criterion | Which applicable trust services criterion cannot be met by CloudNimbus's controls alone |
| **Necessity test** | Is a control at the user entity genuinely **required** for the criterion to be met — or would disclosing it merely move an obligation CloudNimbus already holds? |
| **Capability test** | Can the customer actually perform it? A CUEC describing a setting the customer cannot reach, or telemetry the customer cannot see, is not a control |
| **Agreement test** | Does the contract or the product documentation already put this on the customer? A CUEC is a disclosure of an existing division of responsibility, not a way to create one |
| If any test fails | **Refuse it, and record the reason.** The refusals are as much a part of the description's integrity as the disclosures |
| Communication | How the customer is told: onboarding pack, administrator documentation, annual reconfirmation |
| Non-performance | **What happens if the customer does not perform it.** Required. A disclosure that describes only the intended world is not a disclosure |

**The last field is the one that matters.** CUEC-05 is the clearest case: a customer who does not validate
the payroll export before submitting it has a wrong number reaching a payroll run, and the description says
so rather than implying that every customer performs every disclosed control.
